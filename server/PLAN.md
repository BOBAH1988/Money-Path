---

## Почему переезд дешевле, чем кажется

Перечисли факты, уже верные в коде, — они меняют объём работы:

- **Транспорт изолирован.** Все облачные вызовы идут через одну точку — `src/lib/firestore.ts`
  (реэкспортирует API наружу, остальной код импортирует только его). Это слой, который
  заменяется на HTTP-клиент, а не переписываемое «всё».
- **Local-first уже реализован.** Кэш и очередь в `src/lib/dataStore.ts` (upsert / delete / clear
  + budget plan) работают без сервера. Сервер получает лишь вторую реализацию транспорта.
- **Нет реалтайма.** Код читает `getDocsFromServer` + кэш (pull-модель, `firestore.ts:114-136`),
  `onSnapshot` не используется. Значит достаточно обычного REST без SSE/WebSocket.
- **Idempotency готова.** У операций очереди уже есть `id` (`createId`) — его можно использовать
  как `Idempotency-Key` при повторах, чтобы не дублировать записи.

## Структурный центр: граф зависимостей

Делать блоки надо в порядке зависимостей, указанном ниже. ASCII-схема показывает, что открывает что:

```
[1. ветка + каркас server/]  ──▶ [2. контракт API]        ──▶ [4. аутентификация]
                                            │                       │
                                            ▼                       ▼
[3. хранилище + миграция данных]  ◀────────┴───────────▶  [5. двойной запуск + флаг]
                                                                    │
                                                                    ▼
                                      [6. инфраструктура + переключение]  ──▶ [7. вывод Firebase]
```

Ключевое: **не начинать миграцию данных (шаг 3), пока не определён проект API (шаг 2)**,
и **не переключать трафик (шаг 6), пока не работает обратная связка флага (шаг 5)**.

## Этап 4. Аутентификация

Таблица развилок — после неё ровно один выбор.

| Вариант | Что это на самом деле | Кому подходит |
|---|---|---|
| **A. Оставить Firebase Auth + верифицировать ID-token на сервере** (рекомендуется на этап 1) | Фронт не меняется; сервер через `firebase-admin` проверяет токен, извлекает `uid` и разрешает только свой `uid`. | Минимальный риск и объём; подходит для переезда без паузы разработки |
| B. Свой email+пароль | argon2, refresh/access token, свои страницы входа. Пароли из Firebase **не переносятся** — потребуется сброс пароля для всех. | Хочется полной автономии от Google |
| C. OAuth-провайдеры | Google/Yandex/… подключаются сами на own server, но это та же зависимость от внешних provider-ов. | Нужны сторонние входы без Firebase |

- [ ] Для варианта A: разобраться с `src/context/AuthContext.tsx` (там импорт `firebase/auth`) — он остаётся, меняется только отправка токена в API.
- [ ] ⛔ Никогда не доверять `uid`, присланный клиентом; `uid` брать только из валидированного токена. *Иначе любой может писать в чужой аккаунт — это то, что сегодня делает `firestore.rules`.*
- [ ] Ревокация/мягкий logout на сервере при смене пароля.

## Этап 5. Двойной запуск и переключение

- [ ] Флаг `VITE_DATA_BACKEND = firebase | api` (build-time или runtime-config с прочерком дефолта).
- [ ] Shadow-чтения: новый API читает в фоне показывая старые данные. *Позволяет сравнить и поймать ошибки до cutover.*
- [ ] Dual-write (очень осторожно, под флагом на этапе теста) — переживать конкурентные записи.
- [ ] ⛔ Перед любым рубильником — свежий экспорт данных через пользовательские JSON-архивы (`src/lib/backup.ts`, `scripts/backup.cjs`). *Единственная подтверждённая страховка без биллинга Firebase.*
- [ ] Cutover: переставить флаг в `firebase → api`, зафиксировать SHA, наблюдать за ошибками.
- [ ] Откат: вернуть флаг — 10 минут, без потери данных. Проверен заранее на тесте.

## Развилки — сравнение вариантов

### Стек сервера

| Вариант | Что это на самом деле | Комментарий |
|---|---|---|
| **Fastify + TypeScript** (рекомендуется) | Современный фреймворк, тот же язык, что фронт | Один язык на весь проект, zod уже есть для валидации |
| NestJS | Много «из коробки», но тяжелее и больше магии | Нужен большой сервер с модулями |
| Go / Actix | Быстрый, но второй язык в проекте | Только если сервер станет высоконагруженным |

### СУБД

| Вариант | Что это на самом деле | Комментарий |
|---|---|---|
| **Postgres** (рекомендуется) | Надёжная классика, бэкапы, миграции, типы | Оправдывает себя уже на этом объёме |
| SQLite | Ноль инсталляции, один файл | Ок для одного пользователя, но слабо для конкурентного доступа |
| Оставить Firestore через firebase-admin | Данные там же, но сервер читает их API | Не даёт автономии — цель переезда не достигнута |

### Хостинг

| Вариант | Что это на самом деле | Кому подходит |
|---|---|---|
| **VPS в РФ** (рекомендуется) | Выделенная машина, полный контроль, бэкапы свои | Данные локальны; проще с 152-ФЗ |
| Зарубежный VPS | Дешевле, но данные вне РФ и лаг | Если юрисдикция не принципиальна |
| Managed (Supabase/Neon) | Ноль администрирования | Быстро, но снова зависимость от провайдера |

## Отказы и запасной ход

| Что ломается | Признак | Что делать |
|---|---|---|
| Клиент без сети | Пустой/устаревший кэш, очередь застревает | Очередь + кэш сохранить; проверить airplane-mode тестом до cutover |
| Правила доступа Firestore исчезли | Нужна серверная валидация владельца | zod-валидация + uid из токена (этап 4); не экономить на этом ⛔ |
| Потеря записей при миграции | Расходятся счётчики | Сухой прогон + сверка; стоп до исправления |
| Регресс после cutover | Ошибки в логах, жалобы | Вернуть `VITE_DATA_BACKEND=firebase` — 10 минут, без потери данных |
| Разнобой у пользователя | Данные «пропадают» после перехода | Через `dataVersion` не перезаписывать свежий кэш |

**Порог эскалации:** если расхождение данных не устранено за ___ часов после cutover —
не чинить «на лету», вернуть флаг на Firebase и разбираться в спокойном режиме. Не повторять
blind-push при упавшем CI (правило `docs/workflow.md`).
